# 正式知识整理 Runbook

> **定位**：维护 Agent 在同一上下文内核验并修复既有正式知识的执行步骤。
> **规范依据**：知识分类、融合和质量标准见 `docs/architecture/03-knowledge-model.md`。
> 定时维护流程见 [knowledge-health-check.md](knowledge-health-check.md)；新知识仍由任务 Agent 在上下文完整时直接写入 owner。

---

## 通用约束

- **先有证据再改**：没有现实证据和明确目标 owner，不做语义清理。
- **不过度整理**：单轮深度整理不超预算（如 30 分钟），格式不完美但内容有用的别动。
- **过期内容不留第二副本**：确认失效后从正式 owner 删除；危险操作先备份到 `/tmp`。
- **保持 diff 可读**：一次只做一类；索引更新与内容整理分开提交，不"重排格式 + 补内容 + 修链接"混做。
- **不确定就停止**：归属不明时在最终结果中请求人工决策，不创建 finding 或「待归类」中间文档。

---

## 一、先跑健康门禁

```bash
spec health check
```

先修确定性错误，再处理语义候选。门禁本身不自动改文件。

---

## 二、核验问题

1. 回到当前代码、配置、PRD 片段或权威 owner 验证巡检发现的问题。
   - 先读真实调用点、配置消费字段和当前部署对应配置，不以字段名、旧文档或会话结论代替实现证据。
   - 可执行结论至少用一条实际命令、测试、配置查询或日志证据复核；只看 diff 不算验证。
2. 判断内容类型并确定唯一目标：
   - 业务系统必须怎样 → `biz-knowledge`
   - 仓库或链路是什么 → `repo-knowledge`
   - Agent 如何完成一类任务 → Skill
   - Workspace 必须遵守什么 → `architecture`
   - 未来重复验证 → `biz-tests`
   - 工具自身 bug、脚本缺陷或待办 → `ISSUES.md`
3. 证据不足或 owner 不明确时停止，不为完成整理而猜。

---

## 三、最小修复

先逐项核对本轮是否产生：

1. 系统事实：写入 `biz-knowledge`、`repo-knowledge` 或 `architecture`。
2. 工具经验：写入对应 Skill 的 `SKILL.md`、`references/`、`scripts/` 或 `tests/`。
3. 可重复验证：写入 `biz-tests/`。
4. 工具缺陷：写入 `ISSUES.md`，不混进稳定指南。
5. 故障排查：不保存整份事故记录；只抽取已验证且可能复现的 Failure Mode，按系统事实、诊断方法和回归 case 分别进入上述 owner。

随后执行最小修复：

1. 在目标 owner 的语义章节内融合，不追加会话时间线。
2. 重复内容迁入唯一 owner，其他必要入口改成短链接；没有召回价值的副本直接删除。
3. feature / foundation 调整必须基于适用范围，不按引用次数机械升降级。
4. 当前灰度比例、名单人数、部署工单、运行版本和一次执行结果属于动态状态，不进入稳定 owner；需要追溯时保留在原生平台。
5. 新证据推翻旧假设时直接替换为当前结论；删除被证伪假设及修正时间线，不保留“第一版/第二版假设”叙述。
6. 已证实失效且无消费者的内容先 `mv → /tmp` 再移除；文件年龄不是删除依据。
7. 新建或删除正式文档时同步 canonical `INDEX.md`。
8. 若发现可重复验证缺口，写入 `biz-tests`，不只补一段文字。

---

## 四、验收

1. 重新运行 `spec health check`。
2. 阅读 diff，确认没有引入第二份规则、动态状态、被证伪假设、事故时间线或中间总结。
3. 最终回复说明修改路径和原因；不另建整理报告。
