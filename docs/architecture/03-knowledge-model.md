# 03 - 知识模型与生命周期

> 定位：知识分类、召回顺序、需求活动期入口与直接写入原则的唯一标准。
> 工具无关：本文不规定由哪个 hook、调度器、模型或脚本执行。

## 1. 内容分类

按内容语义匹配第一个命中的 owner：

| 内容 | 唯一 Owner | 何时更新 |
|------|------------|----------|
| 原始需求 | `docs/prd/` | 需求源变化时；正文只读 |
| 描述业务系统必须怎样 | `docs/biz-knowledge/<feature>.md` | 业务规则确认或变化时 |
| 描述业务链路如何落地 | `docs/repo-knowledge/features/<feature>.md` | 链路实现或认识变化时 |
| 描述某仓库是什么、有哪些公共事实 | `docs/repo-knowledge/foundations/<repo>.md` | 仓库公共事实变化时 |
| 告诉 Agent 如何完成一类任务 | 对应 skill 的 `SKILL.md` / `references/` / `scripts/` | 方法、工具或平台机制变化时 |
| 可重复执行的业务验证 | `biz-tests/<feature>/` | 业务规则或回归方式变化时 |
| Workspace 必须遵守的稳定规则 | `docs/architecture/` | 治理标准变化时 |
| 当前需求的工作集与特定约束 | 需求工作区 `AGENTS.md`（dossier） | 需求活动期 |

快速判断：

- “业务上必须怎样” → `biz-knowledge`
- “这条链路如何落地” → `repo-knowledge/features`
- “这个仓库做任何事都要懂” → `repo-knowledge/foundations`
- “Agent 下一步该怎么做” → skill
- “Workspace 一律必须怎样” → `architecture`
- “以后还要重复验证” → `biz-tests`

## 2. 正式知识

### 2.1 业务知识

业务知识描述可验证规则，不复制 PRD 全文，不包含代码实现细节。每篇文档应能追溯到需求源，并关联涉及的实现链路和业务测试。

### 2.2 仓库知识

`repo-knowledge` 使用两个不同维度：

| 目录 | 组织维度 | 判据 |
|------|----------|------|
| `foundations/` | 按仓库 | 任意该仓任务都应知道 |
| `features/` | 按业务链路 | 只在做该链路时需要，即使只落一个仓库 |

Feature 文档保持打平，一篇串起完整链路，不按仓库再次拆分。同一事实只在一个位置维护，其他文档通过链接引用。

### 2.3 可执行知识

Skill 是可执行知识 owner，不只是工具说明：

- `SKILL.md` 定义能力边界、触发意图和任务路由。
- `references/` 保存按需加载的专有机制、前置条件、决策树、操作经验和稳定陷阱。
- `scripts/` 固化需要确定性执行或反复重写的步骤。
- `tests/` 保护脚本契约和高风险解析逻辑。

模型已具备的通用原理不重复维护。业务事实仍归业务知识，仓库与链路事实仍归 repo-knowledge；不能因为某条事实“有操作性”就复制进 Skill。

### 2.4 业务测试

业务测试是业务规则的可执行表达：

- `biz-knowledge/<slug>.md` 与 `biz-tests/<slug>/` 使用相同 slug。
- 业务规则引用覆盖它的测试；测试引用对应规则或 feature。
- 日志查询、部署状态等辅助证据不等同于业务测试。
- 只有未来值得重复执行的 case 才进入 `biz-tests/`。

具体目录、命名和可执行要求以 [`../../biz-tests/README.md`](../../biz-tests/README.md) 为准。

### 2.5 故障知识

故障排查不建立独立内容 owner。一次事故的时间线、logid、临时账号和处置过程留在任务系统、日志平台或 Git；正式知识只吸收可复用的 **Failure Mode**。

满足以下条件时应写入，而不能仅以“环境特定”为由丢弃：

1. 同类触发条件未来可能再次出现；
2. 能描述稳定的适用范围、外部现象和判别证据；
3. 根因已经验证，并能给出处理动作或规避方式；
4. 去掉本次时间、请求 ID 和临时资源后仍有行动价值。

写回时按语义拆分，不复制整份排查记录：

| 可复用部分 | Owner |
|------------|-------|
| 业务规则被违反时的表现 | `biz-knowledge` |
| feature 特有的故障模式 | `repo-knowledge/features` |
| 全仓库、全环境通用的故障模式 | `repo-knowledge/foundations` |
| 跨 feature 的诊断顺序、工具信号和判别方法 | 对应 Skill |
| 可重复构造的防回归 case | `biz-tests` |
| 工具自身缺陷 | `ISSUES.md` |

Failure Mode 至少保留：适用范围、现象、触发条件、判别证据、已验证根因、处理方式；环境名可以作为适用范围，但当前实例数、一次性 logid 和处置时间不进入正文。

## 3. 活动期入口

### 3.1 Dossier

Dossier 是需求活动期的入口，不是知识本体：

- 位置：需求工作区根 `AGENTS.md`
- 内容：一句话目标、需求特定约束、涉及仓库、PRD/plan/知识指针
- 铁律：**Index-Not-Copy**；已有归处的内容只链接，唯一原创内容是需求特定约束
- 生命周期：需求完成后，把已验证且可复用的知识直接写入正式 owner，随后退役 dossier

## 4. 内部组织

分类存储只规定“内容放哪个类”，类内部按发现方式组织。

### 4.1 组织维度

| 目录类型 | 发现方式 | 主组织维度 |
|----------|----------|------------|
| 正式知识（biz-knowledge / features / foundations） | 语义发现（“这是什么”） | 业务 / feature / 仓库 |
| 可执行知识（skills） | 任务发现（“用什么、怎么做”） | 工具 / 平台 / 跨工具流程 |

同一 owner 内只使用一个主组织维度，不交叉按仓库、业务和时间重复分组。

Skill 的公开粒度同时受召回率和注入预算约束。工具名、平台名和常用意图必须出现在始终注入的 description 或集合路由中，但不要求每个工具都拥有独立顶层 metadata。工具较多且边界清晰时，默认采用统一工具入口的三层结构：一个宽描述的集合 Skill 负责召回，`SKILL.md` 按用户表达路由，`references/<tool>/` 与 `scripts/<tool>/` 按需加载；只有需要独立生命周期、独立外部 owner 或无法由集合稳定召回的能力才单独暴露。技术方案、开发、测试、排查等用途只作为跨工具流程入口，不拥有工具实现。

### 4.2 默认打平，按需分组

- owner 根目录默认物理打平，优先通过 canonical `INDEX.md` 的小节进行语义分组。
- 只有同时满足以下条件时才建立物理子目录：
  1. 存在长期稳定的语义边界；
  2. 至少形成两个有实际内容的分组，不为单篇文档建立目录；
  3. 打平索引已经明显影响发现或维护。
- 文件数量只作为触发复查的信号，不自动决定目录结构。
- 不预建空目录，不为未来可能出现的内容提前设计层级。
- 可执行 SOP、平台机制和排查方法归入对应 Skill。

### 4.3 索引所有权

- 每个 owner 根目录维护一对入口：`README.md` 定义稳定契约，canonical `INDEX.md` 登记当前实例条目；二者职责不同，不互相复制。
- 正式知识、需求源和 Biz-Test 各有且只有一个 canonical `INDEX.md`。
- `README.md` 不承载当前条目，新增或删除内容时只更新 `INDEX.md`。
- `features/`、`foundations/` 等语义分组继承 owner 根目录的契约和索引，不另建 README/INDEX；只有被提升为独立 owner 时才建立自己的入口对。
- 父级 `INDEX.md` 可以统一索引子目录内容，索引链接必须使用从该索引出发的完整相对路径。
- 每份被索引文档必须且只能出现在一个 canonical 索引中。
- 索引只负责发现，不复制正文结论。

### 4.4 深度

- 正式知识通常不超过 `owner / semantic-group / document`。
- 超过上述深度时应重新检查分类，而不是继续增加嵌套。

## 5. 召回顺序

涉及某仓库、业务链路或平台机制时，按需召回：

```text
业务规则
  → feature 链路知识
  → 仓库 foundations
  → PRD 原文片段
  → Skill 执行知识
```

规则：

- 命中已有知识时先读，再探索代码。
- 只取当前任务相关片段，不把整份 PRD 或整份 foundation 注入任务。
- `INDEX.md` 只做目录，不复制正文结论。
- 快速索引可以存在于运行时记忆或搜索工具中，但它不是知识事实源。

## 6. 运行时写入

1. Agent 在上下文最完整、事实刚验证时直接更新唯一 owner，不先写摘要、快照或问题记录。
2. 推测和探索过程留在当前会话；只有已验证且未来可复用的事实进入正式知识。
3. 新知识融合进目标文档的语义章节，不机械追加会话时间线。
4. 问题根因中的系统事实写入对应 feature 或 foundation；可复用的排查方法写入对应 Skill；设计决策写入最接近被约束对象的 owner；历史由 Git、任务系统和原始日志保存。
5. 可重复验证直接写入 `biz-tests/`；工具参数和操作经验直接更新对应 skill。
6. 需求特定、尚未稳定的约束只写 dossier，不污染正式知识。
7. 任务结束前执行 knowledge flush：核对本轮已验证事实是否全部进入 owner，并在最终回复声明写入路径；确无可复用知识时明确说明原因。
8. 冲突时先核验现实，再更新 owner；不能让两份文档各保留一版结论。
9. 新建或删除正式文档时同步 canonical `INDEX.md`。
10. 不确定归属时运行 `spec show kb-routing`；仍不确定则保留在当前会话，不创建中间层。
11. 周期维护由同一个 Agent 在同一上下文内完成检查、核验、最小修复和复验；每次使用相同的优先级：确定性 finding → 活动 Issue → 有明确证据的最小知识单元。调度时间不决定检查类型，也不维护轮换游标；没有明确信号时 no-op。只有证据不足、owner 不明或需要业务/架构决策时才上报人工。
12. `biz-tests/` 不做周期业务语义巡检。它由具体任务在产生稳定、值得重复执行的业务 case 时写回；周期维护只通过确定性门禁检查索引、引用、凭证和结构完整性。

## 7. 质量标准

- **可验证**：关键规则有来源、代码位置、测试或日志证据。
- **可定位**：标题、slug 和索引描述能让后续任务发现它。
- **单一事实源**：同一事实只有一个 owner，其余位置只链接。
- **时态正确**：正式知识描述当前有效事实；历史证据留在其原生系统。
- **决策可延续**：容易被重复推翻的设计决策在唯一 owner 中保留当前结论、关键原因、适用边界、重审条件和证据指针；不保存完整探索过程。
- **内容优先**：结构校验用于发现缺口，不因格式不完美拒绝有价值知识。
