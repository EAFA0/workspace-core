# 06 - 文档所有权与单一真相源

> 定位：定义标准层、路由层和原生历史证据的边界，以及内容 owner 的选择规则。

## 1. 三层模型

### 1.1 标准层

定义“是什么、必须满足什么”。每类事实只有一个 owner。

标准层包括：

- `docs/architecture/`：跨目录的稳定原则与知识模型
- 各内容目录的 `README.md`：该目录产物的格式、命名、验收和生命周期
- 各 skill 自己的 `SKILL.md` / reference：该任务域的可执行知识

标准层不写当前落地状态、具体调度频率、历史修复过程或“待启用”计划。

### 1.2 路由层

只回答“什么时候读哪个 owner”，不复述 owner 正文。

典型路由层：

- `AGENTS.md`
- `docs/README.md`、`docs/architecture/README.md`
- skill 的 Route by task
- quickstart
- `spec` 的路由 manifest

路由项应尽量只有：触发条件、逻辑名称、owner 链接。

### 1.3 原生历史证据

记录发生过什么、当前怎样实现，不具有规范权威：

- 平台 adapter、runtime 注册表和配置说明
- Git、任务系统、日志平台等原生历史证据

原生历史证据不作为当前知识 owner。若现实已经改变，应修改正式 owner，而不是从历史记录反向推导当前规则。

## 2. Owner 选择

| 事实 | Owner |
|------|-------|
| 协作与验收质量底线 | `01-core-principles.md` |
| 知识分类、召回、生命周期 | `03-knowledge-model.md` |
| 文档分层与 SSOT | 本文 |
| Biz-Test 结构与追溯 | [`biz-tests/README.md`](../../biz-tests/README.md) |
| 一类任务如何完成 | 对应 Skill |
| 某定时任务或 hook 当前如何挂载 | 对应运行时注册表或配置 |
| 一次变更、事故或迁移的历史证据 | Git、任务系统或日志平台 |

判断规则：

1. 谁最接近被描述对象，谁优先成为 owner。
2. 内容若会随另一个文件同步变化，就不应在当前位置复述。
3. 索引只描述如何找到 owner，不承载 owner 的规则。
4. 稳定概念可在 owner 内自包含；跨 owner 重复不属于“自包含”。
5. Owner 根目录的 `README.md` 与 `INDEX.md` 是契约/实例的入口对；语义子目录默认继承这对入口，不重复建立局部契约或局部索引。

## 3. 标准与执行的关系

- 标准说明结果必须满足什么。
- 执行入口只说明如何到达标准，不能重新定义标准。
- 某动作需要被主动召回时，路由层提供触发词并链接 owner。
- 脚本可以实现确定性校验，但脚本行为必须对应 owner；脚本不是第二份文字规范。
- 平台实现可替换，知识标准不依赖特定 hook、调度器、模型或 CLI。
- 共享 workspace 只承载工具中立的标准、知识、Skill 与验证资产；特定 Agent 的 persona、memory、scheduler、session 和客户端配置属于外部 runtime / adapter，不得成为共享知识的 canonical owner。

## 4. 模块引用

一个 skill 视为一个模块：

- 模块内部可以引用自己的脚本路径。
- 跨 skill 只写“skill 名 + 逻辑工具名 + 用途”，不引用对方内部脚本路径。
- 外部稳定 CLI 可以直接引用命令。
- 代码 import、配置 command 等机器消费路径必须写真实路径，并由可执行检查验证。

## 5. 反模式

发现以下内容应合并到 owner，当前位置删除或改成短链接：

1. 同一规则在多个文件各写一版。
2. 索引中展开实现细节、命令参数或决策背景。
3. 规范中混入时间戳、当前数量、已落地/待启用状态。
4. 为已废弃或空内容写长篇“为什么这里没有东西”。
5. 把 TODO、阶段计划或修复过程写进长期标准。
6. 在文档中教授模型已具备的通用代理能力。
7. 跨 skill 引用易变内部路径。
8. 用历史文档或 adapter 充当当前规则。
9. 复制 PRD、知识正文或 change plan 到 dossier。
10. 为了保持“完整”保留没有真实消费者的第二份规范。
11. 先写中间总结或会话快照，再让另一轮 Agent 重新归纳到正式 owner。

## 6. 写入自检

写入前只问四个问题：

1. 这条事实的 owner 是谁？
2. 当前文件是 owner、路由，还是历史/实现？
3. 未来变化时是否需要同步改别处？若需要，说明正在制造多真相源。
4. 六个月后的读者是否能直接采取行动或获得证据？不能则删除或缩短。

## 7. 变更纪律

- 先确定新 owner，再替换路由并移动旧文档。
- 个人 workspace 直接切换到最终结构，不保留旧路径、跳转页、wrapper 或 symlink。
- 危险清理先 `mv → /tmp`，确认验收通过后再处置备份。
- 冻结历史不重写，只修活跃路由和标准。
- 文档移动后，所有本地链接、章节锚点和 canonical 索引必须保持可解析。
- 完成后必须检查机器消费路径、Markdown 链接和索引一致性。
