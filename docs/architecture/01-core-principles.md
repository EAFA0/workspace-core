# 01 - 协作与验收原则

> 定位：跨工具、跨项目稳定成立的质量底线。
> 不包含：具体代理角色、委派步骤、CLI 选择、调度器或 hook 实现。

## 1. 工作原则

1. **先读真实实现再讨论方案**：涉及代码时先确认调用点、数据流和当前行为，不凭文档摘要猜实现。
2. **最小且聚焦**：只改完成目标所需的内容，不顺手重塑无关结构，不用大改造掩盖局部问题。
3. **保留可恢复路径**：自动化失败时能退回手动方式；危险清理优先 `mv → /tmp`，不做不可恢复删除。
4. **工具损坏不阻塞业务**：能力包或脚本不可用时直接换可验证的替代路径，并让失败在输出中可见。
5. **PRD 只读**：`docs/prd/` 是需求源，不手工改写正文；提炼后的规则进入正式知识库。
6. **Review-before-push**：任务交付的 push 必须得到用户明确批准。固定个人备份仓可由已登记的后台 job 在确定性健康门禁通过后自动同步；该例外不授权发布、部署或向项目仓推送。

## 2. 验收原则

1. **命令实测，不看 diff 就信**：diff 只能说明改了什么，不能证明行为正确。
2. **断言必须可执行**：每条验收标准应给出可运行命令和可观察预期；禁止只写“确认正确”“验证无问题”。
3. **从需求验证，不从实现自证**：断言描述业务或接口应满足的结果，而不是检查“某行代码是否存在”。
4. **先小后大**：先跑最贴近改动的测试，再按风险扩大到构建、回归或环境验证。
5. **独立性按风险选择**：高风险变更应使用干净上下文或独立验证者降低确认偏误；普通改动不强制机械分角色。
6. **失败必须可诊断**：测试或脚本失败时保留 exit code、stdout/stderr 和必要证据，不静默吞错。

## 3. 上下文原则

- 给执行者的是与当前任务直接相关的事实、约束和可验证目标，不是整篇背景材料。
- 需求特定约束应放在需求工作区的 dossier；跨需求知识应放在正式知识库。
- 通用代理操作交给模型判断；这里只长期维护专有知识和不会自然坚持的质量标准。
